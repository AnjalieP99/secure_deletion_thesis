\chapter{Experimental Framework and Methodology}
\label{sec:experimental-framework}

This chapter presents the experimental framework developed to evaluate secure deletion techniques in modern storage environments. The 
framework is designed to assess not only whether a deletion technique prevents data recovery, but also how quickly it operates, how 
consistently it behaves across storage devices, and what limitations affect verification from the host system.

Secure deletion is difficult to evaluate because the deletion request issued by the operating system does not necessarily correspond 
to the physical removal of data from the storage medium. In NAND flash storage, the Flash Translation Layer (FTL) maps logical block 
addresses to physical pages and performs operations such as wear leveling, garbage collection, and out-of-place updates. These 
processes may create or preserve physical copies of data that are no longer visible through the file system. Consequently, a file may 
appear to have been deleted at the file-system level while remnants remain recoverable at lower storage layers.

Previous experimental studies have used different devices, workloads, deletion procedures, recovery methods, and performance metrics. 
This variation makes it difficult to compare findings across studies. The literature therefore identifies the absence of a 
standardized and reproducible evaluation framework as a major methodological gap. The framework proposed in this chapter addresses 
this gap by defining common experimental conditions, measurable evaluation criteria, repeatable testing procedures, and a host-side 
verification methodology.

The study focuses on outcomes that can be observed from the host perspective. It does not assume that a command completion message 
from the operating system or storage controller proves physical destruction. Instead, secure deletion is evaluated using observable 
indicators such as post-deletion data recovery, residual data persistence, deletion latency, performance variability, and differences 
between storage devices.

\section{Research Objectives}
The aim of this thesis is to develop an experimental framework to evaluate the effectiveness, performance, and practical limitations of 
secure deletion techniques in modern storage environments. Although many secure deletion mechanisms have been proposed in the literature, 
their behavior in real-world systems is difficult to verify because of the abstraction layers introduced by file systems, flash 
translation layers (FTLs), and storage controllers. This work therefore focuses on outcomes that are observable and measurable from the 
host perspective.

The objectives of this study are:

\begin{enumerate}
    \item To evaluate the effectiveness of different secure deletion techniques in preventing post-deletion data recovery.
    \item To investigate how long deleted data persists after TRIM and sanitization operations, and to assess the practical implications 
    of data remanence.
    \item To compare the latency characteristics and variability of secure deletion mechanisms, including TRIM, block erase, and 
    cryptographic erase operations.
    \item To examine how filesystem and storage-layer behavior, such as journaling and FTL remapping, influences the effectiveness of 
    secure deletion.
    \item To analyse differences in secure deletion behavior across consumer and enterprise storage devices.
    \item To identify the practical limitations of host-side verification and establish a methodology for evaluating secure deletion techniques 
    under realistic operating conditions.

\end{enumerate}

\subsection{Research Questions}

To achieve these objectives, the following research questions are investigated:

\textbf{RQ1:} To what extent do different secure deletion techniques prevent the recovery of previously stored data from a host-side forensic 
perspective?

\textbf{RQ2:} How does the recoverability of deleted data change over time following TRIM and sanitization operations?

\textbf{RQ3:} What are the latency characteristics and performance variability of TRIM operations across different storage devices and 
filesystem utilization levels?

\textbf{RQ4:} How do filesystem mechanisms and flash translation layer behavior affect the effectiveness of secure deletion techniques?

\textbf{RQ5:} How does secure deletion behavior vary across different SSD implementations and vendors?

\textbf{RQ6:} What are the practical limitations of verifying secure deletion from the host side, and how can these limitations be incorporated 
into an experimental evaluation framework?



\section{Experimental Environment}

\subsection*{Host System}

The experiments were conducted using an Acer Nitro AN515-58 laptop operating as the host system. The system ran Ubuntu 26.04 LTS with a Linux 
7.0.0-28-generic kernel on an x86-64 architecture. The host system firmware version was recorded as V2.21. The use of a consistent host 
operating system and kernel was intended to reduce variation in file-system behaviour, device-driver operation, command execution, and 
communication with the storage devices. The host system provided the operating environment through which the deletion commands, device-inspection 
utilities, system-management commands, and storage-analysis procedures were executed. The experiments were performed using administrative privileges 
where required because device-level inspection and sanitization commands cannot normally be executed by an unprivileged user.


\subsection*{Test Drives}

Two 128 GB solid-state storage devices were used to conduct the experiments. The devices were chosen to represent different storage interfaces and 
controller communication methods. One device used the NVMe interface, while the second device was a 2.5-inch SATA solid-state drive. The first device 
was a Phison E4c PCLe NVMe. It used NVMe version 1.4, had a reported capacity of approximately 128 GB, and used a formatted logical block size of 512 bytes. 
Its recorded firmware version was HPE4BP01. The device reported support for Data Set Management commands and Security Format operations. This device will be 
referred to as the \textbf{NVMe SSD} in the remainder of this thesis. The NVMe SSD was connected to the host system using a JMicron JMS583 USB 3.0 enclosure.

The second device was identified as an EDILOCA ES106 128GB solid-state drive. It used a Serial ATA interface and was reported as compatible with SATA standards up to SATA 
Revision 3.0. The device had a capacity of approximately 128 GB, a 2.5-inch form factor, and a firmware revision of HC2705H3. Its recorded capabilities 
included the ATA SANITIZE feature set, the BLOCK ERASE EXT command, Data Set Management TRIM support, and enhanced security erase support. The two devices 
were used to examine whether differences in storage interface, device implementation, firmware, and supported sanitization commands affected deletion latency 
and post-deletion data recoverability. The devices were not treated as interchangeable. Results were recorded separately for each model because storage 
behaviour varied between controller implementations, firmware versions, capacities, and device interfaces. This device will be referred to as the \textbf{SATA SSD} in the remainder 
of this thesis and it was connected to the host system using a USB 3.0 to SATA adapter.

The connection path between the host system and each SSD formed an additional component of the experimental environment. Since the NVMe SSD was not compatible with the 
host system's M.2 slot and the native SATA port was already occupied, neither storage device was connected directly to the native storage interface of the host. The 
NVMe SSD was connected through a JMicron JMS583 USB 3.0 enclosure, while the SATA SSD was connected through a USB 3.0 to SATA adapter. This arrangement introduces a 
possible translation layer between the operating system and the SSD controller. Depending on the implementation of the enclosure or adapter, a host-level discard request 
may be translated into an equivalent command, partially forwarded, delayed, modified, or not forwarded to the SSD. In the case of USB-attached storage, the host may 
communicate with the bridge using a command such as SCSI UNMAP, while the bridge is responsible for translating that request into the command format understood by the 
underlying SATA or NVMe device. 

The influence of this connection path became evident during the preparation of the NVMe experiment. Ubuntu did not initially recognise discard support through the USB 
enclosure. The enclosure required an explicit configuration that enabled the relevant unmap behaviour. After the configuration was applied, the discard capability was 
verified using the reported discard-granularity and discard-maximum values. The verification confirmed that the host system exposed a discard capability through the 
connection path. However, this verification did not independently demonstrate that every discard request was received and processed by the SSD controller, nor did it 
confirm that the controller physically erased the corresponding NAND pages. The reported capability should therefore be interpreted as evidence of host-visible command 
support rather than proof of end-to-end TRIM or UNMAP execution. This issue is particularly relevant when comparing the NVMe and SATA results. Differences in recovery 
may have resulted from the SSD controller and firmware, but they may also have been influenced by the USB enclosure, the USB-to-SATA adapter, command translation, 
driver behaviour, or the manner in which each bridge handled discard requests. The connection path was therefore retained as a methodological limitation and treated as 
a potential source of variability.


\section{Experiments Conducted}

\subsection{Experiment 1: TRIM and Filesystem-Level Data Recoverability}

This experiment was conducted to investigate the effect of the TRIM operation on the recoverability of deleted data at the filesystem level. The objective was to 
determine whether information associated with a deleted file remained accessible through filesystem metadata, inode structures, the ext4 journal, or the previously 
allocated data blocks after TRIM. The experiment was performed on an SSD formatted with the ext4 filesystem using a block size of 4096 bytes. A test file was created and 
its filesystem metadata and block allocation information were recorded before deletion. The relevant inode and journal structures were subsequently examined to establish 
the state of the filesystem before and after deletion and TRIM.

A 100 MB test file containing random, non-compressible data was created on an ext4 filesystem using a 4096-byte block size. The inode number, file size, block 
allocation, filesystem journal state, and superblock information were recorded before deletion. The test file was then deleted using the rm command, followed by 
synchronisation and an explicit fstrim operation. The following tools were used for analysis:

\begin{itemize}
    \item {ext4magic}: A recovery tool capable of extracting deleted files from ext3/ext4 filesystems using journal data

    \item {debugfs}: A filesystem debugger for examining ext4 internal structures

    \item {dumpe2fs}: A tool for displaying filesystem superblock and group descriptor information

    \item {dd with xxd}: For direct block-level inspection of allocated data blocks
\end{itemize}

The investigation consisted of four complementary stages.
First, the inode was examined using debugfs. The analysis recorded whether the inode remained allocated, whether the block pointers were still present, whether the size 
and block count had changed, and whether the inode remained associated with a pathname. Second, the ext4 journal was examined using dumpe2fs and debugfs. The purpose was 
to determine whether the deletion operation had been recorded in the journal and whether the journal contained file data or only metadata updates. Third, recovery was 
attempted using ext4magic. The tool was directed to the relevant inode and, in a secondary attempt, to the journal start block. This allowed the experiment to test 
whether the journal contained sufficient information to reconstruct the deleted file. Fourth, the previously allocated data blocks were read directly using dd and 
examined with hexadecimal output. Individual journal blocks were also extracted so that the inode state recorded in the journal could be compared with the current 
filesystem state. The purpose of using several methods was to avoid relying on one indicator. A filesystem-level recovery failure alone might reflect a limitation of the 
recovery tool. Similarly, an empty inode alone would demonstrate logical deallocation but would not establish the state of the underlying NAND cells. Combining metadata 
analysis, journal inspection, recovery attempts, and direct block inspection produced a more complete host-side assessment.

\subsection{Experiment 2: Data Recovery After TRIM}
This experiment investigated the effect of TRIM configuration on the host-side recoverability of deleted data from the tested NVMe and SATA SSDs. The experiment compared 
the number of dataset-specific signatures recovered under TRIM-enabled and TRIM-disabled conditions using a forensic recovery procedure. The experiment was conducted on 
the Ubuntu host machine using and tests were performed on the NVMe and SATA SSDs. Before each experimental run, the beginning of the storage device was overwritten with 
zeros to remove existing partition and filesystem structures and the device was prepared with a new GPT partition table and ext4 filesystem.

Discard behaviour was controlled using the filesystem mount options \texttt{discard} and \texttt{nodiscard}. The TRIM-enabled condition used the discard mount option, 
while the TRIM-disabled condition used nodiscard. In the TRIM-enabled condition, an explicit fstrim operation was also performed after deletion.

The experiment was repeated five times for each storage configuration. The repeated runs were intended to assess whether the results were reproducible or whether the 
storage devices produced variable outcomes under nominally identical conditions. Each run used the same dataset allocation, deletion procedure, recovery method, and 
signature-counting procedure.

The experiment therefore treated the following as independent or controlled factors:
\begin{itemize}
\item  SSD type, consisting of NVMe and SATA devices.

\item TRIM configuration, consisting of the nominal TRIM-enabled and TRIM-disabled conditions.

\item Dataset status, consisting of kept, deleted, and post-deletion write datasets.

\item Experimental run, consisting of five repeated runs for each storage configuration.

\item Connection path, consisting of the USB-NVMe enclosure and the USB-SATA adapter.
\end{itemize}

The connection path was included as an important methodological variable because neither SSD was connected directly through a native PCIe or SATA interface. The NVMe 
device was accessed through a JMicron JMS583 USB enclosure, while the SATA device was accessed through a USB-to-SATA adapter. The host-level confirmation did not 
independently prove that every discard request was correctly forwarded to the SSD controller. It confirmed only that the operating system exposed a discard-capable 
path. The effective TRIM condition should therefore be understood as the behaviour of the complete host, driver, USB transport, bridge, and SSD configuration.

\subsection*{Dataset Generation and Allocation}

To enable precise measurement of data recovery, a custom data generation script was developed. The script created unique, searchable signatures within each dataset, allowing 
recovery success to be quantified by counting the number of signatures found after deletion. Each dataset used a dataset-specific signature identifier, allowing recovered 
content to be attributed to its original dataset and enabling recovery to be quantified consistently across experimental conditions.Each dataset contained repeated-signature 
text files, multiple small text files, binary files containing embedded signatures, and checksum information. The mixture was intended to test recovery of both text-based evidence and binary content. 

The experiment included three categories of datasets:
\begin{itemize}
    
\item Kept datasets served as positive controls and were not deleted.

\item Deleted datasets formed the main test group.

\item Post-deletion write datasets were created after the deletion of the test group to evaluate whether subsequent logical writes removed the signatures associated 
with the earlier datasets.

\end{itemize}
The dataset allocation included three kept datasets, two deleted datasets, and three post-deletion write datasets for each TRIM condition. This arrangement allowed 
the recovery procedure to be checked using positive controls while also testing both deletion and later write activity.

This design ensured that for each SSD type and TRIM status, there were 3 kept datasets (positive controls) to confirm recovery tools worked, 2 deleted datasets (test 
groups) to measure recovery after deletion and 3 post-deletion write datasets to test whether new data destroyed old data

For each run, the following procedure was applied:

\begin{enumerate}
\item The SSD was prepared and formatted with an ext4 filesystem.

\item The relevant nominal TRIM condition was configured.

\item Datasets 1 to 5 were created, and datasets 2 and 4 were deleted.

\item The nominal TRIM-enabled condition received an explicit fstrim operation.

\item Datasets 6 to 8 were created after the deletion operation.

\item Datasets 9 to 13 were created under the nominal TRIM-disabled condition.

\item Datasets 10 and 12 were deleted, and no explicit fstrim operation was issued in that condition.

\item Datasets 14 to 16 were created after deletion.

\item The device was scanned using the selected recovery tools.

\item Dataset-specific signature occurrences were counted and recorded for each dataset.

\end{enumerate}
\subsection*{Recovery Procedure}

PhotoRec was used to attempt recovery of deleted datasets. PhotoRec is a widely used open-source data recovery tool that can recover lost files from various storage 
devices. The recovery process involved scanning the entire SSD for recoverable files and searching for the unique signatures embedded in the datasets. 
PhotoRec performes full file carving based on file headers and footers and is able to recover complete files regardless of the filesystem. It is interactive and 
requires user input to specify the source device, file types to recover, and destination for recovered files. PhotoRec was configured to scan the whole partition rather 
than only unallocated space. Scanning the whole partition is necessary when the filesystem may be corrupted or when deleted data may reside in areas not marked as 
unallocated . This approach maximises the chance of recovering residual data from previously allocated blocks. And Recovered files were written to a separate storage 
device within the host system's internal storage to prevent overwriting the target SSD

Since PhotoRec cannot recover original filenames or filesystem metadata , identification of recovered content relied entirely on the embedded signatures. After PhotoRec 
completed the recovery process, the recovered files were analyzed to determine the presence of the unique signatures from the deleted datasets. The number of 
successfully recovered signatures was recorded for each dataset, allowing for a quantitative assessment of data recoverability under different TRIM conditions.

Recovery was quantified using the number of dataset-specific signature occurrences identified in the recovered output. For each dataset, the recovery rate was 
calculated as:

\[
\text{Recovery Rate (\%)} =
\frac{\text{Recovered Signatures}}{\text{Expected Signatures}}
\times 100
\]

A recovery rate of 100\% indicates that all expected signature occurrences were identified in the recovery output, whereas a recovery rate of 0\% indicates that no 
matching signatures were identified. The metric represents host-side recovery by the specified forensic procedure and should not be interpreted as a direct measurement 
of the physical state of NAND flash. Recovery rates were calculated as the mean number of recovered signatures across the five runs, with standard deviation 
reported to quantify variability.

The same experimental procedure, dataset-generation script, TRIM configuration, deletion procedure, and recovery procedure were applied to both storage devices. 
Results were recorded separately for each device to account for differences in device implementation and controller behaviour.

\subsection*{Limitations and Workarounds}

\textbf{TRIM was not Recognized on USB Enclosure}: \\
Initially, Ubuntu did not recognize TRIM support on the USB NVMe enclosure. This was because USB enclosure was unable to automatically pass the TRIM command to the NVMe 
SSD. The Kernel had to be explicitly configured to enable the \texttt{unmap} feature, which is the SCSI equivalent of TRIM.


\subsection{Experiment 3: Testing Recoverability at different fill levels and times intervals}

Experiment 2 was repeated with the addition of a time delay between deletion and recovery to investigate how recoverability changed over time. The experiment was 
conducted at different fill levels of the SSD to assess whether the amount of free space affected the persistence of deleted data. The experiment also recorded the 
execution time of the fstrim operation in order to characterize the host-visible latency associated with issuing discard requests to the storage device. The below 
script was used to automate the process of wiping the drive,creating datasets, deleting them, waiting for a specified time interval, and then attempting recovery. 

The experiment was performed using a controlled test environment in which the storage device was formatted with the ext4 filesystem. Before each experimental sequence, 
the device was unmounted and the beginning of the device was overwritten with zeros before a new GPT partition table and ext4 filesystem were created. The experimental 
filesystem was subsequently mounted at the designated test mount point. The experimental procedure therefore began from a freshly initialized filesystem state, although 
the initial 100 MiB overwrite did not constitute a complete physical wipe of the entire SSD.


Prior to the recovery experiment, the filesystem was filled to a specified target utilisation level. The amount of filler data was calculated from the filesystem capacity 
and the selected fill percentage, after which random data was written in chunks of up to 100 MB until the target utilisation level was reached. The resulting filesystem 
utilisation was recorded before the experimental dataset was created. A dataset of approximately 2.5 GB was then generated for each experimental iteration. Each dataset 
consisted of multiple file types, including text files, a large ZIP archive, numerous small text files, a JPEG image, and a PDF document. Dataset-specific identifiers 
were embedded within the generated files to enable the experimental data to be distinguished from unrelated recovered content. The dataset also included a checksum file 
generated from the experimental files. This provided a reference for the original dataset contents and supported subsequent verification of recovered data.


For each iteration, a unique dataset directory was created to ensure that the experimental data could be distinguished across iterations. The dataset was first created 
and its total size and file count were recorded. The complete dataset was subsequently deleted using rm -rf, followed by sync and a short five-second delay. After 
deletion, the filesystem was subjected to an explicit fstrim operation. Before measuring the operation, filesystem caches were flushed and the Linux page cache was 
cleared. The fstrim command was executed using /usr/bin/time -v, allowing the elapsed, user and system execution times to be recorded. The amount of storage reported as 
trimmed by the command was also recorded. Following the TRIM operation, forensic recovery was attempted after a predefined waiting period. The experiment used different 
recovery delays to examine whether the passage of time following TRIM affected the amount of data observable through the recovery procedure. The configured waiting 
periods were 0, 5, 15 and 30 minutes. At each recovery point, the foremost forensic recovery tool was executed against the test partition using all supported file types. 
The number of recovered files was then recorded in a CSV results file together with the iteration number, waiting period, filesystem fill level, measured TRIM execution 
times and the amount of data reported as trimmed.


The experiment recorded the following variables for each iteration:

\begin{enumerate}
    
\item \textbf{Filesystem fill level}: representing the proportion of the filesystem occupied before the experimental dataset was created.
\item \textbf{TRIM execution time}: including real, user and system time reported by /usr/bin/time.
\item \textbf{Amount of storage reported as trimmed}: by fstrim.
\item \textbf{Recovery delay}: representing the time between completion of TRIM and the beginning of the forensic recovery attempt.
\item \textbf{Number of recovered files}: as reported by the recovery output.
\end{enumerate}

The primary relationship investigated was therefore between the recovery delay following TRIM and the amount of data recovered by the forensic tool. The execution time 
represents the host-visible duration of the discard operation and does not provide direct evidence of when the SSD controller performs internal garbage collection, 
block erasure or other flash-management operations. Consequently, the latency measurement is interpreted as host-observable TRIM latency, rather than as a direct 
measurement of physical data-erasure latency. For each recovery delay, the recovered output was examined and the number of recovered files was recorded. The results 
were then compared across the different waiting periods.

The experiment was repeated under Trim off conditions to provide a baseline for comparison. In the TRIM-disabled condition, the same dataset creation, deletion, and 
recovery procedures were applied, but no fstrim operation was performed. The filesystem was filled to the same target utilisation levels, and the same recovery delays 
were applied. The recovered output was analyzed in the same manner, and the number of recovered files was recorded for each recovery delay. This allowed a direct comparison
of the recoverability of deleted data under TRIM-enabled and TRIM-disabled conditions, as well as an assessment of how recovery changed over time following deletion.
Five seperate runs were performed for each storage device, fill level, and TRIM condition. The repeated runs were intended to assess whether the results were reproducible
or whether the storage devices produced variable outcomes under nominally identical conditions. Each run used the same dataset allocation, deletion procedure, and recovery method.
